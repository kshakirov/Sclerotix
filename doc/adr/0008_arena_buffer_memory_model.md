# ADR 0008: Zero-Allocation Arena Buffer для сборки тела HTTP-запроса

## Статус
Предложено (Целевой ориентир для реализации)

## Контекст
При обработке потока чанков (`Transfer-Encoding: chunked`) наивный подход требует выделения нового массива памяти под каждый прилетающий кусок данных с последующей конкатенацией (`total_body += new_chunk`). В рантайме Python это приводит к агрессивной фрагментации кучи, постоянному перевыделению памяти и непредсказуемым задержкам из-за вызова Garbage Collector. Это недопустимо для высокопроизводительного ядра Sclerotix.

## Решение
Внедрить модель монолитного буфера арены (Arena Memory Buffer) по канонам Кнута и Вирта со следующими правилами управления:

1. **Единое пространство выделения**:
   Для каждого сетевого соединения выделяется один мутабельный массив `body_buffer = bytearray()`. Данный буфер живет внутри лексического замыкания операционного автомата.

2. **Потоковое вымывание служебных данных (On-the-fly Stripping)**:
   Операционный автомат (`run_engine`) на Первом такте полностью отсекает служебные метаданные чанков (Hex-размеры и терминаторы `\r\n`). 
   * Полезная нагрузка (мясо данных) побайтово или блочно дописывается строго в хвост буфера арены через метод `.extend()` или прямое поиндексное заполнение.
   * Граница полезных данных сдвигается автоматически: `current_tail_pointer = len(body_buffer)`.

3. **Изоляция затвора**:
   Чистый затвор `next_state` (Такт 2) не имеет доступа к `body_buffer` и оперирует только логическим регистром оставшегося размера чанка (`in_value`), сохраняя иммутабельность и Тип-3 по Хомскому.

## Последствия
* **Плюсы**: Гарантированное отсутствие лишних аллокаций памяти в цикле парсинга. На выходе из автомата (`State.SUCCESS`) мы имеем идеально чистое, склеенное тело HTTP-запроса, готовое к передаче в бизнес-логику без единой операции копирования.
* **Минусы**: Требуется жесткий контроль максимального размера буфера (Max Body Size) на первом такте во избежание DoS-атак через бесконечный поток чанков.
