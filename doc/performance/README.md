# Sclerotix performance protocol

Этот раздел задаёт постоянный протокол измерений latency и throughput. Он продолжает правило из экспериментальной программы:

> Сначала baseline. Потом одно изменение. Потом повторное измерение.

Документы и канонические запросы хранятся в git. Сырые результаты живут локально в `var/performance/` и не публикуются на GitHub.

## Что сравниваем

Минимальная регрессионная матрица состоит из трёх стабильных сценариев:

| request_id | Метод | Путь | Тело | Назначение |
|---|---|---|---:|---|
| `get_index_empty` | GET | `/index.html` | 0 B | запрос без тела |
| `post_index_16b` | POST | `/index.html` | 16 B | короткое фиксированное тело |
| `put_index_1k` | PUT | `/index.html` | 1024 B | тело, пересекающее вероятные транспортные границы |
| `put_index_5k` | PUT | `/index.html` | 5120 B | тело, заведомо не помещающееся в один `recv(1024)` |

Точное описание запросов находится в [requests.md](requests.md). Сценарий допускается в измерение только после функциональной проверки ожидаемого HTTP-статуса. Нельзя сравнивать серию успешных ответов с серией `404` или ошибок транспорта.

## Локальная структура данных

```text
var/performance/
├── summary.csv
└── raw/
    └── YYYY-MM-DD/
        └── request_id/
            └── run-NNN/
                ├── metadata.env
                ├── results.gob
                ├── samples.csv
                └── report.json
```

- `results.gob` — исходный результат Vegeta без преобразования.
- `samples.csv` — одна строка на запрос; это основная статистическая выборка.
- `report.json` — агрегаты Vegeta для быстрой проверки.
- `metadata.env` — условия конкретного прогона.
- `summary.csv` — одна строка на прогон для анализа изменений по датам и commit.

Форматы описаны в [schema.md](schema.md). Заголовок для локального `summary.csv` лежит в [summary-template.csv](summary-template.csv).

## Профиль baseline

Основной зафиксированный GET baseline снят на `pmd-pims-aio`:

```bash
PROFILE=baseline_remote_get_10k_10s
RATE=10000/s
DURATION=10s
RUNS=5
WORKERS=10
CONNECTIONS=100
KEEPALIVE=false
HTTP2=false
SERVER_CPU=3
VEGETA_CPUS=4,5,10,11
```

Условия машины и результаты находятся в
[machines/pmd-pims-aio.md](machines/pmd-pims-aio.md) и
[baseline-remote-get-10k-2026-10-06.md](baseline-remote-get-10k-2026-10-06.md).
Этот профиль является контрольным для эксперимента со streaming route hash.

Проверка POST после исправления области действия `Content-Length` записана в
[post-validation-2026-10-06.md](post-validation-2026-10-06.md).

Локальный кандидат на профиль регрессии GET после калибровки 2026-10-06:

```bash
PROFILE=baseline_local_get_2k_10s
RATE=2000/s
DURATION=10s
RUNS=5
WARMUP_DURATION=5s
WORKERS=1
CONNECTIONS=10
KEEPALIVE=false
HTTP2=false
SERVER_CPU=1
VEGETA_CPUS=2,3,6,7
```

Перед каждым прогоном обязателен TCP cooldown до фонового уровня `TIME_WAIT`.
Нагрузка выбрана как консервативная точка: одиночная калибровочная ступень
`2000 RPS` прошла без массового роста latency tail, а при `2250 RPS` он уже
появился. Серия из пяти прогонов затем показала, что рабочая машина не обеспечивает
изоляцию от остальных пользовательских процессов: пятый прогон получил сильный
внешний хвост. До повторения на выделенной машине профиль остаётся кандидатом, а
не сертифицированным baseline. Калибровка и ограничения описаны в
[calibration-2026-10-06.md](calibration-2026-10-06.md).

Первоначальный кандидат `baseline_1k_rps_30s`:

```bash
RATE=1000/s
DURATION=30s
RUNS=5
WARMUP_DURATION=5s
WORKERS=10
CONNECTIONS=10000
```

оказался непригоден для локальной рабочей машины: `workers=10` и
`connections=10000` не были получены калибровкой, а совместный запуск генератора и
сервера перегрузил машину. Этот профиль не является нормативным и не должен
повторяться автоматически.

Выбранный профиль нельзя менять между сравниваемыми версиями.
Другая интенсивность, длительность, affinity, число workers или connections
образуют другой именованный профиль.

Локальный GET-профиль задаёт около 20 000 запросов на прогон и около 100 000 на
серию. Фактическое `sample_n` обязательно записывается из `samples.csv`, а не
вычисляется как `rate × duration`: генератор или сервер могут не выдержать
заданную интенсивность.

Для текущей альфы:

```bash
KEEPALIVE=false
HTTP2=false
```

Keep-alive пока не поддерживается сервером, поэтому изменение этого флага создаёт другой эксперимент.

Характеристики локальной испытательной машины и рекомендуемая CPU affinity
зафиксированы в [machines/thinkpad-p51.md](machines/thinkpad-p51.md).

## Процедура одного эксперимента

1. Зафиксировать commit или tag исследуемой версии и убедиться, что рабочее дерево не содержит относящихся к серверу изменений.
2. Зафиксировать машину, ОС, Python, Vegeta, параметры ядра и лимит файловых дескрипторов.
3. Запустить сервер обычным способом и не менять его конфигурацию между сравниваемыми сериями.
4. Выполнить короткий функциональный запрос и подтвердить ожидаемый HTTP-статус.
5. Выполнить warm-up с тем же request template; результат warm-up не включать в выборку.
6. Провести `RUNS` независимых прогонов. Каждый прогон складывать в новый `run-NNN`.
7. Сохранить `results.gob`, затем получить из него `samples.csv` и `report.json`.
8. Записать фактическое число наблюдений, mean, sample standard deviation и latency percentiles в локальный `summary.csv`.
9. Между сравниваемыми версиями менять только исследуемый фактор. Для первого эксперимента это механизм route hashing.

Для локальных измерений используется отдельный запускатель с каноническими
маршрутами `GET`, `POST` и `PUT /index.html`:

```bash
taskset -c 0 python3 run_performance_server.py
```

Он передаёт таблицу тестовых маршрутов существующему epoll-циклу и не меняет
маршруты обычного `run_server_epoll.py`.

## Команда Vegeta

Для каждого запроса используется отдельный targets-файл и, при наличии тела, отдельный body-файл:

```bash
REQUEST_ID=post_index_16b
DATE_UTC=$(date -u +%F)
RUN_ID=run-001
RUN_DIR="var/performance/raw/$DATE_UTC/$REQUEST_ID/$RUN_ID"
mkdir -p "$RUN_DIR"

vegeta attack \
  -name="$REQUEST_ID" \
  -targets="doc/performance/requests/$REQUEST_ID.targets" \
  -body="doc/performance/requests/bodies/body-16b.txt" \
  -header="Content-Type: application/octet-stream" \
  -rate="$RATE" \
  -duration="$DURATION" \
  -workers="$WORKERS" \
  -connections="$CONNECTIONS" \
  -keepalive=false \
  -http2=false \
  -output="$RUN_DIR/results.gob"

vegeta encode -to=csv -output="$RUN_DIR/samples.csv" "$RUN_DIR/results.gob"
vegeta report -type=json -output="$RUN_DIR/report.json" "$RUN_DIR/results.gob"
```

Для GET параметр `-body` не передаётся. Для PUT выирается `body-1k.txt` или `body-5k.txt` согласно `request_id`. `BASE_URL` в канонических targets-файлах намеренно зафиксирован как `http://127.0.0.1:8080`; другой host/port должен быть отражён как отдельная конфигурация эксперимента.

Фактический объём выборки:

```bash
wc -l < "$RUN_DIR/samples.csv"
```

Mean и выборочное стандартное отклонение latency считаются непосредственно по третьей колонке без загрузки всей выборки в память:

```bash
awk -F, '
{
  x = $3
  n += 1
  delta = x - mean
  mean += delta / n
  m2 += delta * (x - mean)
}
END {
  if (n > 1) printf "sample_n=%d mean_ns=%.6f stddev_ns=%.6f\n", n, mean, sqrt(m2 / (n - 1))
  else       printf "sample_n=%d mean_ns=%.6f stddev_ns=NA\n", n, mean
}' "$RUN_DIR/samples.csv"
```

Percentiles для `summary.csv` считаются из сырой выборки методом nearest-rank: после сортировки берётся элемент с номером `ceil(p × n)`. Throughput берётся из `report.json`. Агрегаты Vegeta используются как контроль, а не как замена `samples.csv`.

## Правила сравнения

- Не объединять warm-up и измеряемые запросы.
- Не объединять разные `request_id`, машины, режимы keep-alive или уровни нагрузки.
- Не ограничиваться одним средним: хранить stddev, хвосты и сырые наблюдения.
- Не сравнивать прогоны с разными кодами ответа как производительность одной операции.
- Не удалять неудачные серии молча; помечать их `valid=false` и указывать причину.
- Baseline собственного streaming hash снимается на теге `v0.1.0-alpha.1` до изменения hashing.

## TCP cooldown между локальными прогонами

Текущая альфа закрывает соединение после каждого ответа, а Vegeta запускается с
`keepalive=false`. Поэтому каждый запрос создаёт отдельное TCP-соединение. Сторона,
активно закрывшая его, временно сохраняет запись `TIME_WAIT`, чтобы запоздавшие
сегменты старого соединения не попали в новое соединение с той же четвёркой
адресов и портов.

На loopback клиент и сервер используют один сетевой стек и ограниченный диапазон
локальных портов. Большое число `TIME_WAIT` после интенсивной ступени способно
исказить следующий прогон, хотя само по себе не является утечкой Sclerotix.

Перед каждым измеряемым прогоном:

```bash
ss -s
```

Следующую ступень не запускать, пока число `TIME_WAIT` не вернулось примерно к
зафиксированному перед серией фоновому уровню. Фактическое значение до старта
записывать в metadata. Прогон, начатый поверх большого хвоста предыдущей ступени,
считать невалидным и сохранять как диагностический.
