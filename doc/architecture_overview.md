# High-Level Architecture Overview: Sclerotix Core

Документ описывает макрокомпоненты асинхронного HTTP-сервера Sclerotix и их взаимодействие на основе двухтактного Бэконовского конвейера.

## Функциональная схема потока данных

```text
       [ ФИЗИЧЕСКИЙ УРОВЕНЬ ]       POSIX-сокет (Сырой поток байт)
                                                │
                                                ▼
       [ ОПЕРАЦИОННЫЙ СЛОЙ ]        run_engine (Мутабельный EFSM)
       (Такт 1: Драйвер ввода)                 │
                                               ├─► Arena Buffer (ADR 0008)
                                               │   (Сборка чистого тела)
                                               │
                                               ▼ (Поставка NetworkInput)
       [ ЧИСТОЕ ЯДРО ]              next_state (Иммутабельный DFA)
       (Такт 2: Клик затвора)                  │
                                               ▼ (Квант переключения рельс)
       [ ВЫХОДНОЙ КОНТЕКСТ ]         HTTPRequestContext (Объект запроса)
                                                │
                                                ▼
       [ БИЗНЕС-ЛОГИКА ]            Маршрутизатор ──► Пользовательский Handler
```

## Спецификация макрокомпонентов

### 1. Сетевой драйвер / Диспетчер тактов (`run_engine`)
* **Архитектурный класс**: Регистровый операционный автомат (EFSM).
* **Назначение**: Управление системным циклом `while`. Осуществляет физическое или эмулируемое побайтовое чтение потока, контролирует регистр смещения каретки (`buffer_pointer`), декрементирует регистр длины чанка (`in_value`) и производит потоковое отсечение служебных метаданных (`\r\n`). 
* **Выходной интерфейс**: Генерирует и поставляет строгие атомарные сигналы (`NetworkInput`) для чистой дельта-функции переходов.

### 2. Изолированный затвор (`next_state`)
* **Архитектурный класс**: Чистый детерминированный конечный автомат (DFA, Тип-3 по Хомскому).
* **Назначение**: Атомарное вычисление следующей логической вершины графа на основе пары `(State, NetworkInput)`. Полностью верифицирован в nuXmv по LTL/CTL инвариантам безопасности.
* **Свойства**: Тотальный детерминизм, отсутствие побочных эффектов (I/O, мутации памяти), полное рантайм-стирание типов регистров.

### 3. Буфер Арены (`Arena Buffer`)
* **Архитектурный класс**: Zero-Allocation мутабельный массив (`bytearray`), инкапсулированный в лексическое замыкание (ADR 0008).
* **Назначение**: Потоковое накопление полезной нагрузки (тела HTTP-запроса), исключающее повторные аллокации памяти в куче рантайма.

### 4. Контекст запроса (`HTTPRequestContext`)
* **Архитектурный класс**: Строго типизированная структура данных по Степанову.
* **Назначение**: Транспортировка и постепенное наполнение метаданных запроса (метод, путь, заголовки, ссылка на Arena Buffer) по мере продвижения тактов конвейера.

### 5. Маршрутизатор и Слой приложений (Router & Handlers)
* **Архитектурный класс**: Инфраструктурный безстейтовый слой диспетчеризации.
* **Назначение**: Принятие валидированного объекта `HTTPRequestContext` из финальной точки `State.SUCCESS`, сопоставление URL-пути и вызов соответствующей бизнес-функции.
