# Next Architecture Stage — Single-Pass Streaming Core

## Исходная точка

После закрытия issue #5 в Sclerotix существует рабочий вертикальный pipeline:

```text
socket
  ↓
StreamingRequestParser
  ↓
header automaton
  ↓
framing resolution
  ↓
body automaton
  ↓
Arena
  ↓
SUCCESS / ERROR
```

Парсер сохраняет состояние между `recv()`, поэтому транспортная фрагментация больше не определяет границы синтаксического разбора.

Проверены:

- `Content-Length` body;
- `Transfer-Encoding: chunked`;
- запрос без тела;
- конфликт framing;
- побайтовая подача;
- работа через реальный socket;
- smoke-test под Vegeta.

Рабочая конструкция доказана. Следующая задача — не переписать её ради красоты, а последовательно убрать механизмы, которые после эксперимента стали избыточными.

---

# Три главные архитектурные задачи

## 1. Framing recognition during the first pass

Сейчас header automaton сначала строит таблицу абсолютных смещений, после чего framing определяется отдельным проходом по этой таблице.

Рабочая схема:

```text
bytes
  ↓
header recognizer
  ↓
offset table
  ↓
second pass
  ↓
Transfer-Encoding / Content-Length
  ↓
framing
```

Эта конструкция была полезна: она позволила независимо проверить механизм framing и доказать склейку header/body automata.

Но для конечной архитектуры второй проход не является необходимым.

### Цель

Header recognizer должен одновременно:

1. распознавать структуру HTTP headers;
2. строить offset table;
3. распознавать интересующие framing fields;
4. формировать минимальные framing-регистры.

```text
                    ┌→ offset table
byte → recognizer ──┤
                    └→ framing registers
```

После завершения headers body automaton должен получать уже готовое решение:

```text
NONE
FIXED(length)
CHUNKED
ERROR
```

### Важный принцип

Offset table не удаляется.

Она остаётся ленивым представлением HTTP request для последующих потребителей.

Меняется только одно:

> body framing не должен повторно читать уже распознанные байты.

Один байт должен по возможности обрабатываться один раз.

---

## 2. Bounded input storage instead of growing `extend()`

Текущий `StreamingRequestParser` хранит растущий `bytearray`:

```text
recv
 ↓
input_buffer.extend(fragment)
 ↓
parser
```

Это было правильным механизмом для построения и проверки потокового парсера, но не обязательно является конечной моделью памяти.

Уже обработанные байты продолжают занимать место, а рост `bytearray` может приводить к перераспределению памяти и копированию.

### Цель

Перейти к ограниченному streaming storage:

```text
socket
  ↓
bounded buffer / ring
  ↓
recognizer
```

Основной кандидат — кольцевой буфер, но решение не фиксируется заранее.

Необходимо сравнить как минимум:

- ring buffer;
- sliding window;
- segmented/chunked input storage;
- минимальный собственный механизм поверх `recv_into()`.

### Главный инвариант

Физическая позиция байта в памяти и его логическая позиция в потоке — разные понятия.

Парсер должен продолжать мыслить абсолютными логическими offsets:

```text
absolute stream offset
        ≠
physical buffer index
```

Например:

```text
physical_index = absolute_offset mod capacity
```

если будет выбран классический ring buffer.

Это позволит сохранить математическую модель автомата независимо от конкретной организации памяти.

### Отдельный вопрос

Offset table может ссылаться на данные, которые ring buffer уже хочет переиспользовать.

Следовательно, до реализации необходимо определить lifetime тех частей request, которые должны оставаться доступными внешнему потребителю.

Именно этот вопрос определит окончательную модель буфера.

## 3. Own readiness loop instead of `asyncio`

Текущий socket layer использует `asyncio`.

Это позволило быстро проверить настоящий сетевой pipeline, но скрывает часть операционного механизма, который для Sclerotix является предметом исследования.

Следующий этап — собственный минимальный readiness-driven event loop.

Концептуально:

```text
select / poll / epoll
        ↓
ready fd
        ↓
recv / recv_into
        ↓
connection context
        ↓
StreamingRequestParser.feed()
        ↓
NEED_MORE_DATA / COMPLETE / ERROR
        ↓
wait / send / close
```

Каждое соединение имеет собственное состояние:

```text
fd
  →
connection context
  →
parser closure
```

Event loop ничего не должен знать о HTTP automata.

Его задача минимальна:

- зарегистрировать descriptor;
- узнать о readiness;
- выполнить разрешённую операцию;
- передать полученные bytes соответствующему parser;
- изменить интересующие события;
- закрыть descriptor при завершении.

HTTP semantics остаётся внутри StreamingRequestParser.

# Порядок работы

Эти три задачи связаны, но их нельзя менять одновременно.

Порядок:

```text
1. single-pass framing
        ↓
2. bounded input storage
        ↓
3. own select/poll/epoll loop
```

Причина принципиальная.

Сначала стабилизируем **семантику распознавания**.

Затем меняем **физическое представление входного потока**.

И только после этого меняем **механизм планирования I/O**.

Так при каждом эксперименте меняется только один фундаментальный слой.

---

# Архитектурная цель

После этих трёх этапов Sclerotix должен приблизиться к следующей машине:

```text
             ┌──────────────────────────────┐
fd readiness │                              │
────────────→│ bounded input storage        │
             │          ↓                   │
             │ streaming recognizer         │
             │     ├→ offsets               │
             │     └→ framing registers     │
             │          ↓                   │
             │ body automaton               │
             │          ↓                   │
             │ Arena                        │
             │          ↓                   │
             │ COMPLETE / ERROR             │
             └──────────────────────────────┘
```

Без второго прохода ради framing.

Без бесконечно растущего входного буфера.

Без скрытого scheduler/event-loop слоя между readiness ОС и нашей машиной.

---

# Методологический принцип

Это не попытка заявить буквальный zero runtime overhead для Python.

Наш критерий:

> каждый механизм должен существовать потому, что он необходим модели или среде исполнения; устранимый механизм не должен оставаться только потому, что он удобен.

Поэтому движение идёт не через преждевременную оптимизацию, а через последовательное удаление уже доказанно лишних слоёв:

```text
сначала корректная машина
        ↓
затем наблюдаем механизм
        ↓
находим избыточность
        ↓
убираем её
        ↓
снова проверяем машину
```

Это и есть следующий архитектурный этап Sclerotix.
