У меня есть автомат заголовков и автомат тела. Пока они живут отдельно и называются по-разному. Главный челлендж — посадить между ними простую прослойку без нового архитектурного зверя.

Схема такая:

```text
Header Automaton
        ↓
Router / Dispatcher
        ↓
Body Automaton
```

Автомат заголовков дропает результат. Прослойка смотрит на него и решает:

- тела нет — убиваю ветку и иду дальше;
- есть `Content-Length` — запускаю фиксированное тело;
- пришёл `chunked` — запускаю чанковый автомат;
- режим кривой или конфликтный — дропаю ошибку;
- данных пока не хватает — сохраняю состояние и жду следующий `recv()`.

Вопросы:

- прослойка — это обычная функция или маленький автомат;
- что именно дропает автомат заголовков;
- кто держит Arena и общее состояние соединения;
- где кончается автомат заголовков и начинается автомат тела;
- как не вырастить из простого переключателя отдельного зверя;
- куда уходит управление после пустого или полностью прочитанного тела.

Готово, когда оба автомата проходят запрос подряд, прослойка нормально роутит режим тела, а нарезка данных по `recv()` ничего не ломает.

### @kshakirov — 2026-08-26T06:59:42Z

Уточнили зверя. Это уже не просто dispatcher, а полный `StreamingRequestParser`.

- Без Python-классов: делаем фабрику `make_streaming_request_parser()`, которая возвращает замыкание `feed(chunk)`.
- Замыкание хранит фазу разбора, состояния и регистры обоих автоматов, `input_offset`, `body_write_offset`, растущий `input_buffer` и `body_arena`.
- `handle_connection` владеет сокетом и дропает в `feed()` только новый фрагмент из `recv()`.
- `feed()` мерджит фрагмент в `input_buffer`, крутит текущий автомат и возвращает `NEED_MORE_DATA`, `COMPLETE` или `ERROR`.
- После заголовков внутренний dispatcher выбирает framing: пустое, фиксированное или chunked-тело.
- Первый шаг — переделать автомат заголовков: сейчас он каждый вызов стартует с `METHOD` и не может продолжиться после разрыва заголовков между `recv()`.

Zero overhead здесь — асимптота: не плодим механизмы без необходимости и приближаемся к минимальным накладным расходам, но не заявляем буквальный нулевой runtime cost без измерений.

Первый вертикальный блин фабрики собран в `test_fabric.py`. Пока внутрь подключён только автомат тела — так и задумано для проверки самого принципа.

Что уже фактически работает:

- `make_streaming_request_parser()` создаёт отдельное лексическое окружение;
- возвращённая `feed(input_fragment)` замыкает буфер, конфигурацию автомата и Arena;
- входной фрагмент дописывается в растущий `input_buffer`;
- конфигурация, которую вернул `run_engine()`, сохраняется обратно в замыкании;
- полный `RAW_STREAM` фактически дошёл до `State.SUCCESS`, а полезное тело `Wikipedia` было записано в Arena.

То есть главная гипотеза подтверждена: замыкание может быть долгоживущей операционной обёрткой автомата.

Что побить следующими маленькими заходами:

1. Убрать дубль `input_offset` / `body_input_offset`: в едином `input_buffer` нужно одно смещение следующего непрочитанного байта.
2. Пока запускается только автомат тела, честно держать `Phase.BODY`, а не `Phase.HEADERS`.
3. Убрать лишний `nonlocal input_buffer`: `bytearray` мутируется через `.extend()`, имя не перепривязывается.
4. Добавить `COMPLETE` и `ERROR`: сейчас `feed()` всегда возвращает `NEED_MORE_DATA`, даже когда автомат уже дошёл до `SUCCESS`.
5. После этого прогнать несколько вызовов `feed()` на фрагментах одного и того же потока.

Пока не полируем и не тащим сюда автомат заголовков. Сначала добиваем этот минимальный срез, потом наращиваем зверя.

### @kshakirov — 2026-08-27T06:50:01Z

Ещё один обязательный заход: убрать безусловные `print()` из горячего цикла автомата, но не убивать трассировку для отладки.

Тактика:

```python
if __debug__:
    print(...)
```

- в debug-запуске Python трасса остаётся;
- production запускается с `python -O`, где `__debug__ == False`, и диагностические ветки удаляются из байткода;
- обычный `if DEBUG:` такой гарантии не даёт;
- не прячем в `assert` проверки протокола, лимитов и инвариантов: `assert` тоже убивается флагом `-O`;
- отдельно проверяем через `dis`, что production-байткод не содержит вызовов трассировки.

Это делаем после того, как побайтовый срез устоится: текущая шумная трасса пока нужна как инструмент наблюдения.

Уточнение по трассировке: совмещаем compile-time и runtime уровни.

```python
def make_streaming_request_parser(connection_id, *, trace_enabled=False):
    if __debug__:
        trace = (
            lambda message: print(f"[stream-parser:{connection_id}] {message}")
            if trace_enabled
            else None
        )

    def feed(input_fragment):
        if __debug__ and trace is not None:
            trace("...")

        # обычная работа парсера

    return feed
```

- В обычном debug-запуске фабрика включает трассу только для нужного экземпляра `StreamingRequestParser`.
- Можно держать `trace_enabled=False`, когда простыня логов не нужна даже при отладке.
- При `python -O` ветки `if __debug__` должны исчезнуть из production-байткода.
- Это отдельно проверяем через `dis`, а не принимаем на веру.
- Трассировка живёт в операционной обёртке. Чистые функции переходов по-прежнему не логируют и не получают побочных эффектов.

Оба доходят до `BODY_PARSING_FINISHED`, в Arena лежит ровно `Wikipedia`, `input_offset` не съезжает. Код уже в `dev-buffer`, последний коммит — `4d49b27`.
