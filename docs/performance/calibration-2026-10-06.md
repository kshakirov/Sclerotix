# Локальная калибровка GET — 2026-10-06

Цель: выбрать устойчивую нагрузку для сравнительного baseline, а не определить
максимальную throughput сервера.

## Условия

- Host: ThinkPad P51, характеристики в `machines/thinkpad-p51.md`.
- Commit: `386151b`, tag `v0.1.0-alpha.1`.
- Запускатель: `run_performance_server.py`.
- Request: `GET /index.html`, ожидаемый статус `200`.
- Одно TCP-соединение на запрос: `keepalive=false`.
- Sclerotix: CPU 1.
- Vegeta: CPU `2,3,6,7`.
- CPU 5 свободен как SMT-сосед CPU 1.
- Vegeta: `workers=1`, `connections=10`.
- Длительность ступени: 10 секунд.
- Перед чистыми ступенями `TIME_WAIT` возвращался примерно к фоновому уровню.

Первый прогон `2500 RPS` был начат поверх большого `TIME_WAIT` и исключён. Четыре

| 4 | 3.942 ms | 0.586 ms | 33.734 ms | 64.119 ms | 87.522 ms |
| 5 | 4.867 ms | 0.597 ms | 35.822 ms | 68.791 ms | 95.009 ms |

Низкая медиана при высоких P95/P99 означает длинный правый хвост распределения:
большинство запросов быстрые, но заметная доля периодически ждёт десятки
миллисекунд. Временное накопление очереди является гипотезой, а не доказанным
механизмом; для доказательства нужны синхронные наблюдения CPU и socket/accept
queues.

## Серия baseline-кандидата: 2000 RPS

После калибровки выполнено пять независимых прогонов. Между ними сервер
перезапускался, а `TIME_WAIT` возвращался к фоновому уровню.

| Run | Requests | Throughput | Mean | P50 | P95 | P99 | Max |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 20,000 | 2,000.13 | 0.656 ms | 0.566 ms | 1.379 ms | 2.492 ms | 8.074 ms |
| 2 | 19,999 | 2,000.00 | 0.677 ms | 0.552 ms | 1.313 ms | 3.083 ms | 22.286 ms |
| 3 | 20,000 | 2,000.11 | 0.646 ms | 0.571 ms | 1.376 ms | 2.463 ms | 5.792 ms |
| 4 | 19,999 | 1,999.94 | 1.051 ms | 0.609 ms | 1.767 ms | 15.484 ms | 36.186 ms |
| 5 | 19,998 | 1,999.94 | 348.979 ms | 1.498 ms | 1,462.943 ms | 1,595.869 ms | 1,645.371 ms |

Во всех пяти прогонах получено `100% HTTP 200`, заданный throughput удержан.
Однако пятый прогон непригоден как чистая оценка Sclerotix: после него на CPU 1,
закреплённом за сервером, наблюдались мигрировавшие процессы браузера. `taskset`
ограничивает сам Sclerotix, но не запрещает планировщику ставить другие процессы
на то же ядро. Четвёртый прогон также показывает меньший, но заметный хвост.

Сырые данные серии:

```text
var/performance/raw/2026-10-06/get_index_empty/baseline_local_get_2k_10s/
```

## Решение

`2000 RPS` оставляем кандидатом для сравнительного GET baseline: нагрузка ниже
наблюдаемой переходной области `2100–2250 RPS`, но локальная серия доказала
недостаточность изоляции рабочей машины. Нормативный baseline следует повторить на
выделенной машине либо изолировать CPU 1 от всех остальных процессов, а не только
закрепить на нём сервер. POST и PUT требуют отдельных серий; равная интенсивность
ещё не доказывает равную стоимость разных запросов.

Сырые данные сохранены локально под:

```text
var/performance/raw/2026-10-06/get_index_empty/
```
