# Агрегированные результаты

Сюда заносим только сравнимые результаты законченных прогонов.

Для каждого прогона фиксируем:

- дату и короткое имя эксперимента;
- commit и версию Python;
- параметры сервера и нагрузки;
- throughput и latency;
- распределение горячих функций;
- наблюдение, интерпретацию и следующую проверяемую гипотезу.

Сырые файлы профилировщика хранятся на машине в `~/.local/state/sclerotix-profile/`.

## 2026-10-08 — streaming URL hash после удаления offsets

### Вопрос

Какова allocation-цена потокового FNV-1a, если URL больше не материализуется в
`bytes` перед поиском маршрута?

Сравнивались:

- `5c96915`: runtime без `offset_table`, но со старой материализацией URL;
- `0bf734a`: тот же runtime со streaming FNV-1a, хэшированными бакетами и точной
  проверкой метода, длины и URL непосредственно в исходном `bytearray`.

Перед профилированием полный тракт проверен HTTP-запросами: известный
`POST /index.html` возвращает `200`, неизвестный маршрут — `404`.

### Условия

- Python `3.12.3`;
- Sclerotix на `127.0.0.1:18082`;
- `POST /index.html`, тело `0123456789abcdef`;
- Vegeta `12.13.0`: `5 000 rps`, `10 s`;
- контроль: `50 000` успешных ответов;
- streaming hash: `49 999` успешных ответов;
- Memray `1.20.0`, режим `--trace-python-allocators`;
- результаты нормализованы на один запрос из-за различия серии на один запрос;
- latency и throughput под Memray не интерпретируются.

Сырые профили на `pmd-pims-aio`:

```text
без offsets:    ~/.local/state/sclerotix-profile/sclerotix-allocations-20261008T065451Z.bin
streaming hash: ~/.local/state/sclerotix-profile/sclerotix-allocations-20261008T075418Z.bin
```

### Результат относительно состояния без offsets

| Метрика | Без offsets | Streaming hash | Изменение |
|---|---:|---:|---:|
| Всего запросов | 50 000 | 49 999 | -1 |
| Всего аллокаций | 60 085 379 | 63 242 725 | нормализуется ниже |
| Аллокаций на запрос | 1 201.708 | 1 264.880 | +63.172 (+5.257%) |
| Bytes allocated на запрос | 201 297.688 | 205 240.828 | +3 943.140 (+1.959%) |
| Peak live memory | 24.705 MB | 24.163 MB | описательно, не причинный вывод |

Нормализованная цена хэша на 50 000 запросов составляет около 3 158 611
дополнительных аллокаций и 197.157 MB allocation traffic.

Новые и исчезнувшие источники:

- модуль `hashing`: 1 950 021 аллокация, 75.003 MB — примерно 39 аллокаций и
  1.5 KB на запрос;
- `handler`: снижение с 400 007 до 150 008 аллокаций и с 44.201 MB до
  9.602 MB; материализация URL через `bytes(memoryview(...))` устранена;
- оставшаяся цена распределилась прежде всего между вызовом `sx_hash` и местами
  его вызова в `http_headers_parser`.

### Общий результат относительно исходного runtime

После совместного удаления offsets и добавления streaming hash итог остаётся
ниже исходного состояния с offsets и материализацией URL:

- аллокаций на запрос: -81.350 (-6.043%);
- allocated bytes на запрос: -3 755.327 (-1.797%).

### Вывод

Streaming hash устраняет отдельную материализацию URL и уменьшает стоимость
разрешения маршрута, но текущая реализация FNV-1a через immutable Python `int`
создаёт заметный побайтовый churn. Это реальная цена выбранного физического
представления, а не цена семантики одного 64-битного регистра. Хэш функционально
корректен, но его Python lowering остаётся самостоятельной целью оптимизации.

## 2026-10-08 — удаление legacy `offset_table`

### Вопрос

Какую физическую стоимость создаёт таблица offsets, у которой больше нет
потребителей в современной потоковой модели?

Сравнивались два состояния одного runtime до внедрения streaming URL hash:

- контроль: `08a397f`, таблица offsets присутствует;
- эксперимент: `5c96915`, удалены только `offset_table`, `next_offset_id` и их
  протаскивание через header parser, factory и тестовую обвязку.

### Условия

- Python `3.12.3`;
- Sclerotix на `127.0.0.1:18082`;
- `POST /index.html`, тело `0123456789abcdef`;
- Vegeta `12.13.0`: `5 000 rps`, `10 s`, по `50 000` успешных ответов;
- Memray `1.20.0`, режим `--trace-python-allocators`;
- latency и throughput не сравниваются: этот эксперимент измеряет только
  аллокации под инструментированием Memray.

Сырые профили на `pmd-pims-aio`:

```text
контроль:    ~/.local/state/sclerotix-profile/sclerotix-allocations-20261008T065256Z.bin
без offsets: ~/.local/state/sclerotix-profile/sclerotix-allocations-20261008T065451Z.bin
```

### Результат

| Метрика | Контроль | Без offsets | Изменение |
|---|---:|---:|---:|
| Всего аллокаций | 67 311 479 | 60 085 379 | -7 226 100 (-10.735%) |
| Аллокаций на запрос | 1 346.230 | 1 201.708 | -144.522 |
| Allocation traffic | 10.450 GB | 10.065 GB | -0.385 GB (-3.684%) |
| Peak live memory | 29.347 MB | 24.705 MB | -4.642 MB (-15.818%) |
| `http_headers_parser` allocations | 59 980 074 | 52 930 074 | -7 050 000 |
| `http_headers_parser` allocation traffic | 6.344 GB | 5.975 GB | -0.369 GB |

### Наблюдение и вывод

На одинаковых 50 000 запросах исчезло около 7.23 млн аллокаций. Из них ровно
7.05 млн исчезли из `http_headers_parser`, то есть эффект локализован там, где
удалялась таблица, а не объясняется изменением HTTP-семантики или нагрузки.

`offset_table` была не дешёвой страховочной структурой, а измеримым источником
allocation churn: около 145 лишних аллокаций на запрос. Поскольку потребителей у
неё уже не было, изменение одновременно уменьшает физическую стоимость и удаляет
архитектурный долг. Возвращать таблицу в core оснований нет.

## 2026-10-07 — POST 16 B, 5k rps

### Условия

- Python `3.12.3`;
- Sclerotix на `127.0.0.1:18082`;
- `POST /index.html`, тело `0123456789abcdef`;
- Vegeta `12.13.0`: `5 000 rps`, `10 s`;
- py-spy `0.4.2`: `100 samples/s`, включая idle;
- Memray `1.20.0`, режим `--trace-python-allocators`.

### Нагрузка

- запросов: `50 000`;
- throughput: `5 000.40 req/s`;
- ответы: `50 000 × 200`;
- p50: `0.391 ms`;
- p99: `0.991 ms`;
- max: `3.898 ms`.

Latency этого прогона не используется как чистый performance-baseline из-за вмешательства профилировщика.

### CPU-сэмплирование

В приблизительном окне нагрузки `6–16 s`:

- `49.4%` — ожидание в `epoll.poll`;
- `42.0%` — обработка входных событий в `run_event_loop`;
- `40.1%` inclusive — `feed` потокового парсера;
- основная вычислительная активность внутри `feed` пришлась на `parse_req_header`.

### Аллокации

- всего аллокаций: `67 254 847`;
- всего выделено: `10.439 GB`;
- пик живой памяти: `35.816 MB`;
- приблизительно `1 345` аллокаций и `209 KB` выделений на запрос.

Крупнейшие источники:

- `http_headers_parser`: `6.341 GB`, `59 951 317` аллокаций;
- `factory`: `3.497 GB`, `1 231 007` аллокаций;
- `run_server_epoll`: `512.283 MB`, `5 218 565` аллокаций;
- `make_streaming_request_parser`, `factory.py:25`: `3.278 GB`;
- `Enum.__get__`: `2.226 GB`;
- `parse_req_header`, `http_headers_parser.py:129`: `1.580 GB`;
- `parse_req_header`, `http_headers_parser.py:123`: `1.466 GB`.

### Интерпретация

Наблюдается большой оборот короткоживущей памяти при небольшом пике, а не удержание 10 GB одновременно. Выделение `bytearray(64 * 1024)` при создании каждого request parser объясняет около `3.28 GB`: `50 000 × 65 536 B`. CPU- и allocation-профили независимо указывают на разбор HTTP-заголовков как основной вычислительный и аллокационный центр.

Один короткий прогон не является достаточным доказательством отсутствия утечки. Для проверки удержания памяти требуется отдельный длительный эксперимент и отчёт `--leaks`.
